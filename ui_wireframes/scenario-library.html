The entry-speed window

This is the one derived value on the screen and the reason the library is more than a list. Each feature's geometry admits a band of approach speeds that land on the landing rather than the deck or past the transition. Solve it, don't annotate it.

// Solved once per card at load; memoised by jump geometry hash.
export function solveEntryWindow(jump: JumpSpec): Window | null {
  const { lip, knuckle, landingEnd } = buildProfile(jump);
  const ok: number[] = [];
  for (let v = 2.0; v <= 16.0; v += 0.05) {
    const touchdown = integrateBallistic(lip, v, jump.lipAngle);
    const past  = touchdown.x - knuckle.x;
    const spare = landingEnd.x - touchdown.x;
    if (past >= 0.40 && spare >= 0.40) ok.push(v);
  }
  if (!ok.length) return null;                // geometry admits no safe speed
  return { min: ok[0], max: ok[ok.length - 1],
           centre: (ok[0] + ok[ok.length - 1]) / 2 };
}
  • Render null honestly. A feature with no safe speed shows no viable entry speed at this geometry — not an empty bar that looks like a loading state.
  • Reuse the window in the workbench. Region 8 of the workbench sheet shades the approach-speed slider with this band, so a rider sees they are short before they solve.
  • One shared axis across cards. All window bars use the same speed domain, otherwise two cards' bars are not visually comparable.
  • Recompute on geometry change, never on render. Memoise by a hash of the jump spec; this loop is ~280 integrations per card.

Acceptance checks

  • Every jump card's window is computed from its own geometry — editing a preset's lip angle in the schema moves its bar with no UI change.
  • A geometry with no viable speed renders the worded empty state, not a zero-width bar.
  • Tab counts match the filtered row count exactly, including when the filter empties a collection.
  • Wide tables scroll inside their card; the page itself never scrolls horizontally at 360px.
  • Loading a preset then pressing Solve run in the workbench produces a run whose entry speed sits inside the advertised window.
  • Card actions are reachable by keyboard in DOM order and the whole card is not a nested-interactive trap.
