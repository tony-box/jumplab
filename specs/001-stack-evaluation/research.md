# Phase 0 Research: Technology Stack Evaluation

**Feature**: `001-stack-evaluation`  
**Decision date**: 2026-08-24  
**Status**: Selected for planning; implementation remains gated by the validation exercises below.

## Decision Summary

Use a static, offline-capable browser application with these boundaries:

| Stack area | Selection | Verified release baseline |

| Durable local data | IndexedDB through Dexie; `localStorage` only for small UI preferences | Dexie 4.4.5 |

All JavaScript, Rust, and WASM dependencies MUST be exactly pinned in lockfiles. The versions above
are the evidence snapshot, not permission for floating ranges.

## Evaluation Method

### Hard Gates

A candidate is rejected regardless of weighted score if it cannot:

1. Preserve cross-platform deterministic fixed-step physics from deterministic inputs.
2. Model articulated 2D rigid bodies, contact, revolute/prismatic joints, PD motors, limits, and
   bounded motor force or torque.
3. Keep solving off the UI thread and support progress, stale-run rejection, and cancellation.
4. Run after first load without a network connection on the supported browser matrix.
5. Expose accessible DOM equivalents for canvas and chart information.
6. Support deterministic browser workflows, screenshots, and canvas pixel checks.
7. Use a license compatible with redistribution in a browser application.

### Weighted Rubric

Candidates passing the gates are scored from 1 to 5 in each category and normalized to 100.

| Criterion | Weight |
| --- | ---: |
| Physics correctness, determinism, and numerical validation | 25 |
| Browser compatibility and offline behavior | 15 |
| Runtime responsiveness and performance | 10 |
| Accessibility and rendered-output testability | 10 |
| Maintainability and boundary clarity | 15 |
| Dependency maturity, security, and license | 10 |
| Debugging and observability | 5 |
| Build complexity and migration risk | 10 |

Scores summarize evidence for comparison; a score never overrides a failed gate.

## Detailed Decisions

### Decision: React 19 with strict TypeScript 7 and Vite 8

**Rationale**: The wireframes already name React component boundaries and require dense synchronized UI
state, accessibility semantics, stable `data-od-id` attributes, and responsive layouts. React 19 is
stable; strict TypeScript gives one typed vocabulary across UI, schemas, worker messages, and generated
WASM bindings. Vite provides a typed React template, static production output, worker bundling, WASM
asset handling, and a modern-browser production target compatible with the clarified browser matrix.

**Alternatives considered**: Preact, vanilla TypeScript/custom elements, Next.js.

**Constraints**:

- Client-side rendering only; no React Server Components or runtime server.
- Use CSS custom properties and CSS Modules, not a utility CSS framework, so wireframe tokens and
  fixed dimensions remain directly reviewable.
- Use React Router for two representative spike routes; production routes are deferred to later
  feature specifications.
- Use Lucide React for standard icons and preserve the wireframe's one-primary-action rule.

### Decision: Rust Rapier 2D deterministic physics kernel compiled to WASM

**Rationale**: Rapier 2D supplies rigid bodies, colliders, CCD, revolute and prismatic joints, joint
limits, PD position/velocity motors, maximum motor impulse, snapshots, and serialization. Its
`enhanced-determinism` feature provides bit-level cross-platform determinism for IEEE 754-2008 targets,
including WASM, when initialization values and insertion order are deterministic. A thin Rust kernel
keeps ramp geometry, anthropometry, pose interpolation, entry-speed-window analysis, joint setup,
fixed stepping, telemetry, and deterministic math in one domain. The same crate can run native
analytical tests and compile through `wasm-bindgen` with generated TypeScript declarations.

**Alternatives considered**: Direct `@dimforge/rapier2d-deterministic` use, Box2D WASM, custom solver.

**Constraints**:

- Pin Rust 1.98.0 in `rust-toolchain.toml` with edition 2024.
- Pin `rapier2d = 0.35.2` with `enhanced-determinism`, `serde-serialize`, and `wasm-bindgen` features.
- Do not enable `simd8`; it is a different determinism domain and conflicts with enhanced determinism.
- Any transcendental values used to initialize physics MUST use Rapier's re-exported `nalgebra`
  `ComplexField`/`RealField` operations, never platform `Math.sin`/`Math.cos` or Rust primitive trig.
- Construct all bodies, colliders, and joints in canonical ID order.
- Set aerodynamic drag, tire/terrain friction, and unmodeled linear/angular damping to zero and prove
  those invariants with regression tests.
- Teleporting dynamic bodies is forbidden after initialization; use forces, impulses, and joint motors.
- TypeScript may visualize authored keyframes but MUST consume Rust-generated pose samples and speed
  windows for authoritative values.
- The WASM boundary accepts and returns serialized validated payloads, not live Rapier handles.

### Decision: Dedicated physics worker with immutable frame replay

**Rationale**: A dedicated worker gives one owner per app instance, isolates CPU-heavy fixed-step
solving, and matches the wireframe request/result contract. The main thread renders only immutable
frames. Cancellation terminates the active worker and starts a fresh initialized worker; the UI also
rejects responses whose `runId` is not current. This meets the 250 ms cancellation target even if a
WASM solve batch cannot process a cancel message immediately.

**Alternatives considered**: Shared Worker, main-thread solving.

**Protocol rules**:

- Commands: `init`, `solve`, `sample-pose`, `analyze-speed-window`, `cancel`, `dispose`.
- Events: `ready`, `progress`, `result`, `pose-sample`, `speed-window`, `error`.
- Progress is monotonic and emitted at least every 100 ms or 5%, whichever occurs first.
- Fixed-step order and output are independent of message timing and display frame rate.
- Transfer large frame buffers as transferable `ArrayBuffer` values where measurement proves useful.

### Decision: Canvas 2D for the stage; SVG for charts

**Rationale**: Canvas 2D is widely supported across the target browsers, directly fits the full-stage
painter in the wireframes, supports explicit DPR scaling, and is straightforward to replay from an
immutable frame index. The scene does not need WebGL, a retained object graph, textures, or 3D. Charts
benefit from semantic SVG nodes and D3's proven scales/line generators, while data tables remain the
accessible source of truth.

**Alternatives considered**: PixiJS/WebGL, SVG-only stage, Recharts, fully custom chart math.

**Constraints**:

- Simulation state never lives in canvas objects.
- Main-thread Canvas 2D is the compatibility baseline; `OffscreenCanvas` is optional only after a
  measured cross-browser benefit.
- Every canvas has accessible backing metrics/status content in the DOM.
- Expose test-only deterministic frame seeking and pixel sampling behind a non-production test hook.
- Use `ui_wireframes/rendered_html/` as the screenshot, layout, styling, and demonstrated-interaction
  reference. Use the matching wireframe sheet for behavior and data meaning.
- Do not transplant prototype metrics, kinematic approximations, local state, or inline scripts into
  production services or count them as evidence that a feature works.

### Decision: Zustand for app state; Zod for every trust boundary

**Rationale**: Zustand supplies a small external store with selective subscriptions for the scenario,
runs, baseline, solver status, and frame index. Explicit actions preserve the wireframe's immutable-run
rules without Redux ceremony. Zod provides runtime validation and TypeScript inference for scenario
files, IndexedDB records, worker messages, and WASM payloads.

**Alternatives considered**: Redux Toolkit, context/reducer only; Valibot, manual guards.

**Constraints**:

- Persistence is explicit through repositories; no generic store-persist plugin may bypass migrations.
- Physics inputs are validated and normalized before crossing the worker boundary.
- A metric always carries `value`, `unit`, and `source`; unavailable values remain `null`.

### Decision: Dexie/IndexedDB plus versioned JSON scenario files

**Rationale**: IndexedDB is asynchronous, transactional, and stores structured data and blobs. Dexie
adds safer transactions, schema upgrades, and simpler error handling while supporting Chrome, Edge,
Firefox, Safari, iOS Safari, and Chrome Android. Scenario export uses a human-inspectable JSON file
validated by Zod/JSON Schema. The File System Access API is not required because support is not broad
enough; use Blob downloads and file inputs.

**Alternatives considered**: `idb`, raw IndexedDB, `localStorage`, cloud persistence.

**Constraints**:

- IndexedDB stores scenarios, run metadata, and optional cached run frames.
- `localStorage` stores only small UI preferences named by the wireframes.
- Import validates before mutation and runs version migrations in memory; failure leaves current state
  and the database unchanged.
- Request persistent browser storage where available but treat denial/eviction as recoverable; keep
  export available and surface storage errors.

### Decision: Vite PWA service worker with prompt-based updates

**Rationale**: The service worker precaches the application shell, fonts, presets, worker bundle, and
WASM so core workflows work after the first online load. A prompt-based update avoids changing the
physics/model version during an open scenario or run.

**Alternatives considered**: no offline worker, server-rendered application, hand-written cache logic.

**Constraints**:

- Production requires HTTPS; localhost is allowed for development.
- Cache names include the app and schema version.
- Save current work before activating a new service worker.
- Do not cache user scenario files in Cache Storage; they belong in IndexedDB or explicit exports.

### Decision: Vitest, Rust tests, Playwright, and axe

**Rationale**: Vitest shares Vite's module behavior for TypeScript unit/integration tests. Native Rust
tests validate equations, constraints, energy accounting, determinism, and convergence. WASM parity
tests compare native and browser hashes. Playwright projects cover Chromium, Firefox, WebKit, branded
Chrome/Edge, and emulated tablet viewports; it supports offline emulation and screenshot comparison.
Axe supplements manual accessibility review.

**Alternatives considered**: Jest/Cypress, unit-only testing, manual-only browser testing.

**Constraints**:

- Pin screenshot generation to one CI OS/container because browser rendering varies by host.
- Playwright's direct service-worker inspection is Chromium-only. Run functional offline workflows in
  every engine; inspect service-worker internals only in Chromium.
- Playwright WebKit is not a substitute for release smoke tests on real Safari/iPadOS. Run the release
  matrix on actual devices or a real-device browser service.
- Use deterministic app states/frame seeking; fixed sleeps are forbidden as the sole synchronization.

## Benchmark and Validation Exercises

### Standard Scenario Benchmark

The initial reproducible benchmark is:

- Hardware class: 2022-era mainstream laptop, Intel Core i5-1235U or equivalent/slower, 16 GB RAM,
  integrated graphics, plugged in, normal performance mode.
- Exact device, OS build, and browser version recorded with results.
- Scenario: 10 simulated seconds, fixed `dt = 1/960 s`, 12 dynamic rigid bodies, up to 11 joints,
  front and rear wheel contact, suspension, rider PD motors, CCD, force/energy telemetry, and 240 Hz
  output sampling.
- Method: one warm-up, then 20 solves; p95 MUST be under 5 seconds. Progress MUST appear before
  completion; cancellation MUST settle within 250 ms.
- UI replay: 60 frames/s with p95 direct-control feedback below 100 ms.

### Mandatory Physics Spike

Before later full-screen features begin, implement one table jump, one articulated rider, one hardtail
bike, and one full-suspension bike in the Rust kernel. The spike passes only when it demonstrates:

1. Native and WASM output hashes match for the same canonical scenario.
2. Repeated browser runs are byte-identical across Chromium, Firefox, and WebKit.
3. Revolute rider motors enforce target, stiffness, damping, limits, and maximum torque.
4. Prismatic suspension reports travel and impulse without energy creation beyond tolerance.
5. Wheel contact, takeoff separation, CCD, motor work, contact impulse, and energy residual are either
   measured from the core or explicitly remain `pending-core` with a reason.
6. The standard benchmark passes or a measured optimization path exists without relaxing determinism.

Failure of items 1-4 reopens the physics-engine decision. Failure of item 5 keeps affected metrics
unavailable; it does not permit estimates labeled as measured.

### Browser and Offline Spike

Build a minimal route with the worker/WASM asset, one saved scenario, and one canvas replay. After a
successful online load, disable the network and verify load, edit, save, solve, replay, export, and
import in all Playwright engine projects. Complete real-device smoke checks for current Safari,
previous Safari, iPadOS Safari, and Android Chrome before release.

## Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| Rust/WASM increases build complexity | Keep one small physics crate; generate TypeScript bindings; provide one `npm` orchestration command |
| Determinism broken before Rapier initialization | Keep all geometry and anthropometric preprocessing in Rust; use deterministic nalgebra functions and canonical insertion order |
| Required telemetry is unavailable from Rapier APIs | Prove each metric in the physics spike; instrument impulses/work in the wrapper; leave unsupported values pending |
| Worker termination causes expensive WASM reinitialization | Measure initialization; keep module bytes cached; initialize a replacement before accepting the next solve if needed |
| IndexedDB data is evicted | Request persistence, show save failures, and retain versioned file export/import |
| Service-worker update mixes model versions | Prompt for update, save first, and version caches, schemas, and solver together |
| Screenshot tests vary by host | Generate/compare on a pinned CI image and use semantic/pixel invariants for canvas essentials |
| Playwright does not run actual Safari | Add real Safari/iPadOS release smoke coverage; WebKit remains the fast CI signal |
| Rapier or Rust upgrade changes outputs | Pin versions; require golden-scenario, convergence, and native/WASM parity review before update |
| Rendered HTML looks functional despite using mock values and local demonstration scripts | Mark it as non-functional reference material; compare pixels/interactions while proving physics, persistence, worker, offline, and accessibility behavior independently |

## Revisit Triggers

Reopen the relevant decision if any of these occurs:

- The mandatory physics spike fails determinism, contact, motor, or telemetry gates.
- Standard scenarios miss the five-second p95 after measured optimization.
- A supported browser cannot load the WASM worker or complete offline workflows.
- Canvas 2D cannot maintain 60 frames/s on the benchmark device.
- Rapier, React, Vite, Dexie, or Playwright loses maintenance support or reports an unresolved critical
  vulnerability.
- A new product requirement adds collaboration, server-side accounts, 3D, lateral steering, or native
  mobile delivery.
- Scenario or solver migrations cannot preserve physical meaning.
